# Playbook conventions (shared by every playbook)

Every playbook in `.claude/skills/` follows these rules. Each one references this
file rather than repeating it. If a playbook and this file disagree, the
playbook's own **Critical (MUST)** list wins for that playbook.

---

## 1. The app in one paragraph

Sacred Texts is a static, offline-first PWA. **All content, CSS and JS live in
`index.html`** (~16.7k lines, ~2.8MB, with fonts embedded as base64). `sw.js`
is the service worker, `manifest.json` the PWA metadata. There is no build
step, no server, no package manager and no backend. The only network feature
is the optional **Live Session** (Supabase Realtime Broadcast, off unless
`SESSION_CONFIG` is filled in). Hosting is GitHub Pages from `main`:
`https://zboon.github.io/SacredTexts/`.

Read `README.md` (content format, fonts, cache bump, copyright) and
`CONTRIBUTING.md` (section branches, one-array rule) before changing anything.

## 2. Where work items live

| Concept | Here |
|---|---|
| Work item | GitHub **issue** in `zboon/SacredTexts` |
| Work item type | Issue template / label: `bug` (from `bug_report.md`) or `user-story` (from `user_story.md`). Anything else is a task. |
| Acceptance criteria | The Gherkin block in the issue body (**Acceptance criteria** for stories, **Fixed when** for bugs) |
| Comments / discussion | Issue comments + PR conversation |
| State | Open/closed + the `claude:*` labels below |
| Linking a PR to a work item | `Closes #N` in the PR body (GitHub links and auto-closes on merge) |
| Release notes / technical notes / testing scope | Sections of the PR description (see `dev-issue`) |

### Status labels

Create a label if it does not exist yet. Never remove labels a human added.

| Label | Set by | Meaning |
|---|---|---|
| `claude:in-progress` | `dev-issue` | Claude is working on this issue |
| `claude:blocked` | any | Claude hit a blocker; a human must look |
| `claude:completed` | `dev-issue` | PR is open for this issue (remove `claude:in-progress`) |
| `claude:tested` | `test-issue` | Exploratory test pass done, results posted |
| `claude:reviewed` | `pr-review` | Automated review posted on the PR |
| `claude:regression` | `regression-pack` | Issue has automated regression coverage |

## 3. GitHub access

Use whichever is available, in this order:

1. **GitHub MCP tools** (`mcp__github__*`) — cloud Claude Code sessions. Load them with ToolSearch if they are deferred.
2. **`gh` CLI** — local Claude Code, GitHub Actions (`claude-code-action`).

| Action | MCP tool | `gh` equivalent |
|---|---|---|
| Read issue + comments | `issue_read` | `gh issue view N --comments` |
| Comment on issue | `add_issue_comment` | `gh issue comment N --body-file f.md` |
| Labels | `issue_write` (labels) | `gh issue edit N --add-label x` |
| Create PR | `create_pull_request` | `gh pr create` |
| Read PR / diff / files | `pull_request_read` | `gh pr view N`, `gh pr diff N` |
| PR review with line comments | `pull_request_review_write` (create) → `add_comment_to_pending_review` → `pull_request_review_write` (submit_pending) | `gh api repos/{o}/{r}/pulls/N/reviews` |

Never write a bare `#123` in chat output to the user — use the full issue/PR URL.
Inside GitHub comments and commits, `#123` is fine (GitHub auto-links it).

## 4. Every GitHub post Claude writes

Be concise. Every comment, review, or PR body ends with this footer:

```markdown
<!-- claude-playbook: {playbook}; issue: {N}; run: {runId} -->
<sub>Claude session: {sessionUrl} · playbook `{playbook}`</sub>

---
_Generated by [Claude Code](https://claude.ai/code)_
```

- `{sessionUrl}`: the claude.ai/code session URL in a cloud session, or
  `$GITHUB_SERVER_URL/$GITHUB_REPOSITORY/actions/runs/$GITHUB_RUN_ID` in Actions.
- The HTML comment is the machine-readable marker. Before posting, look for an
  earlier comment with the same `claude-playbook` + `issue` marker. If you are
  re-running the same step, **edit that comment** (or post a clearly labelled
  re-run) instead of stacking duplicates.
- Address the requester with `@login` at the top when replying to a request.

## 5. Branches and commits

- **Base branch:** `main`, unless the issue or requester names another one, or
  the harness assigns one (a cloud session's designated branch always wins).
- **Section content:** if the issue is purely content for one section and the
  requester asks for the section branch, base on `section/{name}` and follow
  `CONTRIBUTING.md`: only that section's array, **no version bump**.
- **Branch name:** `claude/{issueNumber}-{short-kebab-slug}`, e.g. `claude/42-burdah-chapter-3-audio`.
- **Commit messages:** `#{issueNumber}: {imperative summary}`, e.g.
  `#42: Add audio link to Burdah chapter 3`. Every commit on the branch carries
  the prefix. Add any attribution trailers the harness asks for.
- **Never** force-push someone else's branch, push to `main` directly, or merge a PR.

## 6. The version bump (non-negotiable on PRs into `main`)

Installed phones only see a change when the cache version changes. When a PR
into `main` changes `index.html` (or `sw.js`, `manifest.json`, icons), bump
**all three together** to the next number:

| File | Line |
|---|---|
| `sw.js` | `const CACHE = 'sacredtexts-vNNN';` |
| `index.html` | `const APP_VERSION = 'vNNN';` |
| `index.html` | `<meta name="app-version" content="vNNN">` |

Make the bump the last commit. If `main` moved and bumped too, merge `main` in
and re-bump to (main's version + 1). Section-branch PRs do **not** bump.

## 7. Validation (run before every push)

### 7.1 Static check

Run from the repo root. It must print three OKs.

```bash
python3 - <<'EOF'
import re, json, subprocess, tempfile, sys
ok = True
s = open('index.html', encoding='utf-8').read()
js = '\n;\n'.join(re.findall(r'<script(?![^>]*\bsrc=)[^>]*>(.*?)</script>', s, re.S))
with tempfile.NamedTemporaryFile('w', suffix='.js', delete=False, encoding='utf-8') as f: f.write(js)
r = subprocess.run(['node', '--check', f.name], capture_output=True, text=True)
print('JS syntax:', 'OK' if r.returncode == 0 else 'FAIL\n' + r.stderr[-2000:]); ok &= r.returncode == 0
app  = re.search(r"const APP_VERSION = '(v\d+)'", s).group(1)
meta = re.search(r'<meta name="app-version" content="(v\d+)"', s).group(1)
sw   = re.search(r"const CACHE = 'sacredtexts-(v\d+)'", open('sw.js').read()).group(1)
same = app == meta == sw
print(f'Versions: APP_VERSION={app} meta={meta} sw.js={sw}', 'OK' if same else 'MISMATCH'); ok &= same
try: json.load(open('manifest.json')); print('manifest.json: OK')
except Exception as e: print('manifest.json: FAIL', e); ok = False
sys.exit(0 if ok else 1)
EOF
```

A single JS syntax error blanks the **entire** app, so this check is not optional.

### 7.2 Run the app

```bash
python3 -m http.server 8765    # run in the background; app at http://localhost:8765/index.html
```

`localhost` counts as a secure context, so the service worker registers and
offline behaviour can be tested. Opening `index.html` as `file://` does **not**
register the service worker.

### 7.3 Browser

Chromium is pre-installed for Playwright in cloud sessions
(`PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers`). Never run `playwright install`
there. Load the app, wait for `load` plus about 1s, and treat any `pageerror` as a failure.
**Ignore** network errors for third-party hosts (Google Fonts, YouTube,
Supabase). Sandbox proxies often break those, and the app is built to survive
without them.

## 8. Things that are never acceptable

- Changing the bundled **KFGQPC Uthmanic Hafs** font bytes (licence forbids modification or subsetting) or deleting `OFL.txt`.
- Adding copyrighted content (modern lyrics, copied translations). See README "content & copyright".
- Committing a Supabase **service-role** key. Only the anon/public key may appear in `SESSION_CONFIG`.
- Renaming an existing `localStorage` key (`mawlid-favs`, `mawlid-marks`, `mawlid-dalail-place`, `mawlid-theme`, `mawlid-reciter`, `mawlid-play-rate`, `mawlid-spread`, `mawlid-client-id`, `mawlid-venue-code`, `mawlid-last-session`) without a migration. Users would silently lose their bookmarks and favourites.
- Putting a new network fetch on the startup path. The app must open with no signal.
- Approving or merging PRs. A human does the final QC and merge.
